# v1.0.5 设计文档：智能检索与领域补白

> 版本目标：智能为主（检索与推理机制升级），领域补白为辅（2 张专卡）。
> 前置：v1.0.4 已落地 Verification Gate（G1-G6）、修复三级分类、回归清单。
> 文件额度：当前 git 跟踪 195 / ClawHub 上限 200；本版本新增 3 个内容文件（195 → 198，留 2 缓冲）。

## 1. 背景与问题

- 检索机制为静态单轮：9 类任务分类 → 固定路由表 → 一次加载。复杂/跨类/模糊问题路由不准。
- Debug Playbook §3"快速验证路径"为线性步骤，不随证据分支与剪枝。
- 模糊提问（"画面不对""卡"）直接进入路由，缺少意图澄清环节。
- 领域空白：Mesh Shader / Task Shader 无专卡（仅 indirect_commands 顺带覆盖 GPU-driven）；桌面窗口集成（SDL/GLFW/Win32）无专卡（当前仅 Android）。

## 2. 方案（已确认：方案 B）

三项智能能力内聚为一个检索循环协议文件（不拆散，避免互相引用与额度浪费）；证据驱动决策树落在 playbook 内容本身（模板 + 22 个 playbook 全量改造）；领域补白 2 张专卡。

否决的替代方案：
- 方案 A（三机制三文件）：5 额度用满，零缓冲，决策树规范文件与 playbook 模板重叠。
- 方案 C（单文件总控）：单文件臃肿，违背仓库模块化惯例。

## 3. 新增文件（3 个）

### 3.1 `00_expert_entry/progressive_retrieval.md` — 检索循环协议

五阶段循环：

```text
R1 查询分解：复杂问题拆为子问题（对象链路 / 平台 / 症状三维度），每个子问题标记目标模块
R2 意图澄清：信息不足时先问再查——判定标准（缺平台？缺现象细节？缺报错证据？假设冲突？）
              + 最小提问清单（每项都是"补齐即可路由"的证据，一次 ≤3 项）
R3 首轮路由：现有 task_routing_rules 的 9 类路由（保持不变，作为循环入口）
R4 证据评估：回答前自检——每个子问题标注置信度（高/中/低），低置信 = 资料缺口
R5 二轮定向检索：仅对低置信子问题定向补载（playbook 决策表指向的 API 卡 / case）
终止：全部子问题高置信，或触及 retrieval_policy §4 最小文件上限
```

与 Verification Gate 的边界：检索循环管"回答前找齐证据"，Verification Gate 管"结论前过 G1-G6"。循环的输出（证据清单 + 置信度）是 Gate 的输入，二者串联不重叠。

### 3.2 `03_api_manual/06_pipeline/mesh_shader.md` — Mesh Shader 专卡

- 内容：Task/Mesh pipeline 创建链路、`vkCmdDrawMeshTasks*`、meshlet 数据布局、与 indirect_commands 的 GPU-driven 衔接。
- 约束：Android 移动端支持有限，适用边界必须显式标注；`[SPEC]` 与 `[ENGINE]` 严格区分。

### 3.3 `03_api_manual/02_surface_swapchain/desktop_windowing.md` — 桌面窗口集成专卡

- 内容：SDL / GLFW / Win32 入口、窗口最小化=pause、resize/DPI 变化→swapchain recreate、framebuffer resized 处理。
- 约束：与 android_surface_lifecycle 卡对等镜像，共享"尺寸变化→swapchain 依赖组重建"的回归规则。

## 4. 就地升级（不占额度）

### 4.1 证据驱动决策树：playbook §3 改造

模板 §3"快速验证路径"从线性 5 步改为决策表：

```md
| # | 检查（成本升序） | 结果 A → 下一步 | 结果 B → 下一步 | 剪枝（排除的假设） |
|---|---|---|---|---|
| 1 | Validation Layer | 有 VUID → §5 根因表定位 | clean → 检查 2 | — |
| 2 | RenderDoc: draw call 是否提交 | 无 draw → 提交链路分支 | 有 draw → 检查 3 | 排除 §2 的 P2 descriptor 假设 |
| 3 | Primitives culled 计数 | = 输入数 → cull/winding 分支 | 正常 → 检查 4 | 排除 §2 的 P0 cull 假设 |
```

- 改造范围：模板 + `04_debug_playbooks/README.md` 规范说明 + 18 个 playbook 文件的 24 个小节全量落地 §3。
- §2 原因排序表保持不动，决策表剪枝列必须引用 §2 的假设编号（P0/P1/P2）。

## 5. 验收标准

1. pytest 全过（含新文件反引号引用检查）、`git diff --check` 干净。
2. git 跟踪文件 195 → 198（≤200）。
3. 18 个 playbook 文件的 24 个小节 §3 均为决策表格式，剪枝列与 §2 假设表对应。
4. 新会话行为差异：模糊提问（如"画面不对"）先给最小提问清单而非直接路由；复杂跨类问题先分解再路由。

## 6. 回归测试问题（人工抽查）

1. 问一个模糊问题（"画面不对"），验证输出为意图澄清清单（≤3 项）而非直接路由结论。
2. 问一个跨类问题（黑屏 + Android + 性能），验证先分解为子问题并逐个标注置信度。
3. 打开任一 playbook，验证 §3 决策表剪枝列引用 §2 假设编号。
4. 问 Mesh Shader 在 Android 的可用性，验证回答标注适用边界与来源等级。
5. 问 GLFW resize 处理，验证路由到 desktop_windowing 卡并带 swapchain 重建链路。
